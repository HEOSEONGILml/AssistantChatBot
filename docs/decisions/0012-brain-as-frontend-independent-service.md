# 0012. 두뇌는 화면과 독립된 WebSocket 서비스로 만든다

- 상태: 채택
- 날짜: 2026-10-15
- 수정: [0011](0011-python-brain-local-sidecar.md)의 "Tauri 앱이 함께 띄우고 함께 정리한다", [0006](0006-user-provided-api-keys.md)·첫 버전 스펙 3.3절의 "키는 Tauri(Rust)가 보관"

## 배경

0011에서 두뇌를 파이썬 프로세스로 정했다. 두뇌 설계 중 처음에는 Tauri(Rust)가 두뇌를 자식 프로세스로 띄우고 표준 입출력으로 중계하는 방식을 제안했다.
사용자가 원칙을 정했다. **두뇌는 고정이고 화면은 바뀔 수 있다**(예: 나중에 Android). 두뇌는 화면에 의존하면 안 된다.
표준 입출력 방식은 "Tauri가 띄운 자식 프로세스"를 전제로 해서 이 원칙에 맞지 않는다.

## 결정

- 두뇌는 혼자 실행되는 서비스다. **WebSocket**으로 화면과 통신한다. 프로토콜은 `docs/brain-protocol.md`가 기준이다.
- 두뇌 코드를 **핵심**(Signal → Reaction, 전송 방식을 모름)과 **전송 계층**(WebSocket)으로 나눈다.
- 지금은 localhost에서만 받는다. 시작할 때 무작위 토큰·포트를 데이터 폴더의 `brain.json`에 쓰고, 화면은 `hello`로 토큰을 보낸다.
- **두뇌가 API 키를 보관한다.** 파이썬 `keyring`으로 OS 자격 저장소에 둔다. 화면은 `set_key`로 넘기기만 한다.
- Windows에서는 편의상 Tauri가 두뇌를 띄운다(이미 떠 있으면 접속만). 두뇌는 누가 띄웠는지 모른다.

원칙은 사용자가 정했고, 전송 방식·인증·키 위치는 사용자가 기술 판단을 맡겨 Claude가 정했다.

## 검토한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| 표준 입출력 + Rust 중계 | 포트를 열지 않는다. 앱과 수명이 같다 | 두뇌가 Tauri 자식 프로세스여야 한다. 다른 화면이 쓸 수 없다 | 화면 독립 원칙에 어긋난다 |
| 로컬 HTTP 서버(REST) | 익숙하다 | 두뇌가 먼저 보내는 선발화에 SSE나 폴링이 더 필요하다 | WebSocket이 양방향이라 더 단순하다 |
| 키를 화면이 보관하고 두뇌에 넘김 | 기존 `keys.rs`를 쓴다 | 화면마다 키 보관을 다시 만들어야 한다 | 두뇌가 키를 쓰는 주체이므로 두뇌가 갖는다 |
| 토큰 없이 localhost만 | 단순하다 | 브라우저의 웹페이지도 localhost WebSocket에 접속할 수 있다 | 대화 내용이 새어 나갈 수 있다 |

## 결과

- 평가 스크립트와 다른 화면이 같은 두뇌 핵심·프로토콜을 쓴다.
- 기존에 Tauri로 저장한 키는 저장 형식이 달라 한 번 다시 넣어야 한다(사용자는 개발자 본인과 팀).
- Android에서 두뇌가 어디서 돌지(폰, PC, 서버)는 Android 작업 때 정한다. 다른 기기에서 접속하게 되면 인증·암호화를 다시 정한다.
