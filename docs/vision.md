# 제품 비전

사용자가 컨셉을 공개하는 만큼 누적한다. 사용자가 직접 말하거나 확인한 것만 적는다. Claude가 혼자 정한 규칙이나 확인받지 않은 해석은 적지 않는다.

다마고치 시절(2026-10-14 ~ 10-20)의 비전은 git 기록에 있다 (`git show 4b8c747:docs/vision.md`).

## 상위 컨셉 (확정, 2026-10-21)

> **사용자의 화면 히스토리를 파악해서, 사용자가 작업 맥락을 일일이 설명하지 않아도 하고자 하는 일과 니즈를 빠르게 알아듣는 computer-use 에이전트 시스템.**

- UFO²나 Claude Cowork만큼 전문적이지 않아도 된다. 그들은 실행은 잘하지만 맥락을 사용자가 직접 주고 작업을 일일이 지시해야 한다 (사용자).
- screenpipe처럼 사용자 화면 히스토리를 파악한다. screenpipe는 기억만 하고 일은 하지 않는다 (사용자).
- 이 둘을 잇는 자리가 이 프로젝트의 자리다. 사례 조사: [references/similar-products.md](references/similar-products.md)

## 핵심 컨셉: 조수 (확정, 2026-10-21)

- 프로젝트 성격을 **다마고치에서 조수로** 바꾼다. → [0022](decisions/0022-pivot-to-assistant.md)
- 강아지는 돌아다니지 않고 **화면 한 자리에** 있다.
- 사용자가 **도움을 요청하면** 강아지가 대답하거나 **실제 작업을 처리한다**.
- 방향은 일반적인 **computer-use 조수**다. 다만 처음부터 복잡한 기능을 넣지 않는다.
- **첫 기능은 인터넷 브라우저 제어**다.
- 조작 대상은 따로 띄운 브라우저가 아니라 **사용자가 지금 보고 있는 브라우저 창**이다.

## 없애는 것 (확정, 2026-10-21)

- 기분과 반응.
- 찌르기·쓰다듬기·던지기 등 **강아지와의 상호작용 전부**.
- **웹 버전**. PC 앱 하나로 간다.
- 지금 있는 **Jev 기능 전부**. Jev는 구조를 만들어 가며 필요하다고 판단되면 그때 쓴다. 필요 여부는 만들면서 알게 된다 (사용자).

## 에이전트를 만드는 순서 (확정, 2026-10-21)

- **1단계: Claude Code로 구현한다.** Claude Code라는 완성된 에이전트 제품을 그대로 쓴다.
- **2단계: Claude Code 부분을 직접 설계한 에이전트로 대체한다.**
- → [0023](decisions/0023-claude-code-first-then-own-agent.md)
- **Claude Code의 동작 원칙은 하네스 문서(.md)가 정하고, 데이터는 데이터 계층과 주고받는다** (사용자). → [0029](decisions/0029-claude-code-harness-and-session-per-task.md)
- **작업 하나 = 세션 하나** (Claude 제안, 사용자 수용). 지난 맥락은 Claude Code 세션이 아니라 데이터 계층에서 찾는다.
- **Claude Code는 파이썬 Agent SDK로 띄운다** (Claude 제안, 사용자 수용). → [0029](decisions/0029-claude-code-harness-and-session-per-task.md), [스파이크](spikes/2026-10-21-agent-sdk-claude-code.md)

## 구조: 입력 → 에이전트 → 출력 (확정, 2026-10-21)

- 구조는 **입력 계층, 에이전트 계층, 출력 계층** 순서로 설계한다 (사용자).
- 구조 설계는 **확장성**을 염두에 둔다. 사용자가 보며 작업하는 프로그램(브라우저, 슬랙, 카카오톡, 폴더 창, 소스트리 등)은 종류가 많다. 프로그램마다 따로 설계하지 않는다 (사용자).

### 입력 계층

- **입력 계층은 요청만 받아 그대로 에이전트에 넘긴다** (사용자). 맥락은 에이전트가 화면 기록에서 직접 찾아본다. → [0026](decisions/0026-input-layer-passes-request-only.md)

### 화면 기록 (백그라운드)

- 화면 기록은 계층 사이를 흐르는 단계가 아니라, 요청과 상관없이 **백그라운드에서 도는 작업**이다 (사용자). 에이전트가 참고하는 데이터 출처다.
- **사용자가 보고 있는 창의 상황이 핵심이다** (사용자).
- **순간만 찍으면 사용자 히스토리를 놓친다** (사용자). 창을 떠날 때의 마지막 모습만으로도 부족하다. 창 안에서 스크롤·페이지 이동·메시지 읽기 같은 일이 많기 때문이다 (사용자).
- 기록은 **공통 관찰 + 선택적 강화** 두 층이다 (Claude 제안, 사용자 수용). → [0024](decisions/0024-observation-common-plus-enrichment.md)
  - 공통 관찰: 어떤 프로그램이든 같다. 창 정보, 화면 캡처, 접근성 트리.
  - 선택적 강화: 더 좋은 정보원이 있는 프로그램만 덧붙인다. 예: 브라우저의 주소·페이지 내용.
  - 새 프로그램은 공급자 하나를 더해 지원한다.

### 출력 계층

- **출력 계층은 사용자 인터페이스만 해당한다** (사용자). 입력 계층처럼 프론트다.
- **컴퓨터에 행동하는 것은 백엔드가 한다** (사용자). → [0028](decisions/0028-output-layer-is-ui.md)

### 1단계 기록기: screenpipe (사용자 방향, 2026-10-21)

- 1단계는 **기술 프로토타입**이라 빠르게 만든다 (사용자).
- 화면 히스토리 기록은 1단계에서 **screenpipe 소스 빌드(CLI)**를 쓴다. 완성품 앱의 유료 플랜은 검토하지 않는다. 사용자는 라이선스를 무시하라고 했다. 참고로 소스 빌드의 회사 업무 사용은 평가 목적 7일까지만 무료다.
- 공개 코드에서 확인한 것 (2026-10-21): `npx screenpipe record`로 기록, `localhost:3030`의 REST 검색 API, MCP 서버(`screenpipe-mcp`). 기록 방식은 바뀔 때만 찍기 + 접근성 트리 우선·OCR 보조로, [0024](decisions/0024-observation-common-plus-enrichment.md)와 같은 모양이다.
- 1단계 조합: screenpipe(기억) + Claude Code(에이전트, MCP로 히스토리 검색, `--chrome`으로 브라우저 조작).

### 데이터 계층 (Claude 제안, 사용자 수용, 2026-10-21)

- 데이터마다 저장소·쓰기·읽기·관리 주체를 정했다. → [0027](decisions/0027-data-layer-ownership.md)
  - 화면 기록: screenpipe가 쓰고 관리한다. 에이전트가 MCP로 읽는다.
  - 대화·작업 기록, 스케줄 작업: 백엔드 SQLite. 백엔드가 쓰고 관리한다. 에이전트는 대화·작업 기록을 MCP로 읽는다.
  - 설정·키: 단축키는 화면, 키는 백엔드.
- 데이터마다 쓰는 주체는 하나다. 에이전트는 자기 작업에만 갇히지 않고, 백엔드 도구를 불러 앱 기능을 쓸 수 있다 (사용자). → [0032](decisions/0032-schedule-creation.md)

### 인증 (사용자, 2026-10-21)

- Claude API 키는 고려하지 않는다. **Claude Code 구독 로그인**만 고려해 설계한다 (사용자).
- 화면은 API 키 입력 대신 **로그인**을 요청한다 (사용자).
- 백엔드는 키 저장(keyring)과 `set_key` 처리를 걷어냈다. 백엔드와 [프로토콜 문서](backend-protocol.md)는 v6로 바뀌어 `set_key`·`no_keys`가 없다. 현재 앱(`app/src`)은 아직 v5라 `set_key`·`no_keys`가 남아 있고, 화면 계획에서 v6로 바꾼다.

## 스케줄 작업 (확정, 2026-10-21)

- 자동화 스케줄을 염두에 둔다. **스케줄링은 직접 구현한다** (사용자). screenpipe의 pipes를 빌려 쓰지 않는다. → [0025](decisions/0025-own-scheduler.md)
- 스케줄은 **스케줄 탭에서 추가**하는 것이 기본이고, **에이전트에게 메시지로** 시켜도 된다. 에이전트를 통하면 **확인받고** 만든다 (사용자). → [0032](decisions/0032-schedule-creation.md)

## 여러 작업 (사용자, 2026-10-21)

- 작업은 하나만 있지 않다. 여러 작업이 함께 있다 (사용자).
- 사용자는 **각 작업의 진행 상태**와 **스케줄 상태표**를 한곳에서 볼 수 있어야 한다 (사용자).
- 작업 지시·알림·패널은 **마우스로** 접근한다. 단축키는 불편하다 (사용자, 2026-10-21).
- 접근 경로는 **강아지 클릭 하나**다. 말풍선은 두지 않는다 (사용자, 2026-10-21).
  - 강아지를 누르면 **패널**이 열린다. 패널에는 **알림·작업·스케줄** 탭이 있다 (Claude 제안, 사용자 확정).
  - **작업 지시는 작업 탭에서, 스케줄 지시는 스케줄 탭에서** 한다 (사용자, 2026-10-21). 작업 지시 입력칸은 작업 탭 맨 아래에 있다.
  - 스케줄은 자유 글이 아니라 **정해진 양식**으로 넣는다. 양식은 작업 지시서 데이터 명세([0032](decisions/0032-schedule-creation.md))를 따른다 (사용자, 2026-10-21).
  - 패널에서 작업을 누르면 그 작업의 **대화 기록**을 본다.
  - 스케줄을 누르면 그 스케줄의 **작업 지시서**와 **히스토리(대화 내역)**를 본다 (사용자, 2026-10-21).
  - **스케줄도 Claude Code 세션 하나**다. 그래서 스케줄과도 대화할 수 있다 (사용자, 2026-10-21). → [0032](decisions/0032-schedule-creation.md)
  - **작업 지시서는 수정할 수 있어야** 한다 (사용자, 2026-10-21).
  - 패널에 **설정** 탭을 둔다. 그 안에서 Claude Code의 **권한 모드**를 고른다 (사용자, 2026-10-21).
  - 패널에 **사용량** 탭을 둔다. Claude Code **구독 사용량 한도**를 보여 준다 (사용자, 2026-10-21).
  - 새 소식은 강아지의 자세와 배지로 알린다 (Claude 제안, 사용자 확정).
  - 배지는 소식의 성격별 개수를 따로 보여 준다 (사용자, 2026-10-21).
    - 빨강: 답이 필요한 소식 (사용자)
    - 초록: 새 소식, 즉 끝난 작업 (사용자)
    - 노랑: 못 한 작업 (Claude 제안, 사용자 확정)
- 강아지는 **화면 오른쪽 아래, 작업 표시줄 위**에 있다 (Claude 제안, 사용자 확정).
- 핵심은 **화면 공간을 많이 차지하지 않는 것**이다 (사용자). 목록이 길어지면 페이지로 나눈다 (사용자).
- 작업마다 **사용자와 주고받은 대화 기록**이 보여야 한다 (사용자). 예: "결제할까요?"에 바로 답하지 않고 되물으면, 그 물음과 답이 작업 안에 쌓인다.
- 화면 디자인 결과: [design/2026-10-21-output-ui](design/2026-10-21-output-ui/README.md)
- 키 입력 요청 대신 **Claude 로그인 요청**을 보인다 (사용자). 설정 창의 키 입력칸은 뺀다 (Claude 제안, 사용자 수용).
- 입출력 인터페이스는 작업 하나를 대화 하나로 본다 (Claude 제안, 사용자 수용). → [0030](decisions/0030-io-interface-task-as-conversation.md)

## 기억 (확정, 2026-10-21)

- 조수는 **기억한다**. 예: 아침에 찾게 한 상품을 오후에 "아까 그거"라고 해도 알아듣는다. 무엇을 얼마나 기억할지는 아직 정하지 않았다.

## 할 일로 남기는 것 (확정, 2026-10-21)

- **RAG 고도화**: 의미 검색(임베딩) 등. 1단계는 에이전트가 키워드·기간 검색 도구로 찾는다 (사용자). → [0031](decisions/0031-retrieval-by-agent-tool-search.md)
- **먼저 도움 건네기**: 강아지가 작업 중인 창을 들여다보고 먼저 도움을 건넨다. 처음 목적에 있었지만 이번에는 넣지 않는다.

## 플랫폼 (확정, 2026-10-14)

- **Windows PC를 먼저** 만든다. → [0022](decisions/0022-pivot-to-assistant.md)
- **1단계는 개발자 PC에서 실행한다** (사용자, 2026-10-21). 저장소를 받아 `uv sync`, `npm install` 뒤 `npm run tauri dev`로 띄운다. 설치 파일 배포는 설계하지 않는다.
- Android는 사용자가 지시할 때 별도로 한다.
- **백엔드는 화면에 의존하지 않는다** (2026-10-15). → [0022](decisions/0022-pivot-to-assistant.md)
